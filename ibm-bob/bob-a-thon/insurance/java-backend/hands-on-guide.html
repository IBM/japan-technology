2026-09-30 版

このハンズオンについて

あなたは今日、生命保険契約管理システムの Backend API チームに配属されました。設計書は残っていません。運用チームからはアラートが上がり、保守案件と新機能の要望が積まれ、フロントエンドは骨組みのまま止まっています。

この 2 時間で、IBM Bob と一緒に「配属 1 週目のエンジニア」がやることを一通り体験します。

# パート 時間 Bob のモード ここでできるようになること
0 準備・イントロ 8 分 — 環境を起動し、Bob の 3 つのモードを使い分ける
1 リバースエンジニアリング 25 分 Ask → Agent 設計書のないコードから 4 つの設計文書を復元し、生成物をレビューする
2 運用: SlowResponseTime アラート対応 10 分 Ask アラート → メトリクス → ログ → コードの順に原因を絞り込む
3 保守 A: 遅延除去とコネクションプール 12 分 Agent → Ask 遅延コードを除き、並列負荷で HikariCP の挙動を Before / After で比べる
4 保守 B: N+1 問題の検出と修正 18 分 Ask → Plan → Agent SQL の「本数」で性能問題を測り、一括取得に直す
5 開発: 契約キャンセル API 20 分 Plan → Agent DTO / Flyway / Service / Controller / テスト / E2E を Bob と進める

7 まとめ 5 分 — Bob の使いどころと、人間が確認すべきことを整理する
合計 120 分

対象者

  • IT エンジニア（Java 経験の有無は問いません。Spring Boot / REST API / データベースの基礎知識があると理解が早くなります）
  • IBM Bob IDE の基本操作（フォルダを開く、チャットに入力する）ができる方

使用技術

Java 21 / Spring Boot 3.2.5 / PostgreSQL 15 / Flyway / Hibernate / HikariCP / Prometheus + AlertManager + Grafana / Vite + Vue 3 + vue-router / IBM Bob

  • コードブロックは Mac/Linux（bash） と Windows（PowerShell） の 2 つを必ず対で載せています。HTML 版では上部のタブで OS を選ぶと、ページ全体の表示が切り替わります
  • 「Bob に依頼」の枠には、使うモード（Ask / Plan / Agent）とプロンプトの全文を載せています。そのままコピーして Bob のチャットに貼り付けてください

Part 1 — リバースエンジニアリング: コードから設計書を復元する

所要時間 25 分モードAsk→Agent

学習目標

  • 設計書がないシステムを、Bob を使ってコードから理解できる
  • API 仕様書・アーキテクチャ概要書・基本設計書・オンボーディングガイドの 4 文書を docs/ に生成できる
  • 生成物をレビューして、誤りや根拠のない記述を見つけられる（このハンズオン全体で最も大切な姿勢です）

シナリオ

前任者はこのシステムの設計書を残さずに異動しました。あなたが最初にやるべきことは、コードを読んで設計書を復元し、チームが同じ理解に立てるようにすることです。ただし、Bob が書いたものを鵜呑みにしてはいけません。

進め方（パイプライン方式）

4 文書を 1 つずつ順番に「依頼 → 待つ → レビュー」すると 25 分に収まりません。Bob が次の文書を生成している間に、前の文書をレビューする流れで進めます。

時間 Bob あなた
0〜3 分 — 講師の状況説明を聞く。docs/ が空であることを確認
3〜8 分 API 仕様書を生成 生成を待つ間に、controller/ のファイル名とエンドポイントをざっと眺める
8〜13 分 アーキテクチャ概要書を生成 API 仕様書をレビュー
13〜18 分 基本設計書を生成 アーキテクチャ概要書をレビュー
18〜21 分 オンボーディングガイドを生成 基本設計書をレビュー
21〜25 分 妥当性確認の質問に回答 オンボーディングガイドをレビュー、振り返り

プロンプトを書くときの 3 つの約束

本パートのプロンプトはすべて次の方針で書いてあります。自分でプロンプトを書くときも守ってください。

  1. 入力ファイルのパスを明示する — Bob に「何を読むか」を任せない
  2. 出力の見出し構成を固定する — 生成物の粒度が受講者ごとにばらつかないようにする
  3. 「コードに書かれていないことは推測せず『不明』と書く」を必ず入れる — 根拠のない記述を防ぐ

"customerId=$cid"

$sw.Stop()
"HTTP $($response.StatusCode)  $($sw.Elapsed.TotalSeconds)s  $($response.RawContentLength) bytes"

次に、このリクエストで発行された SQL の本数を確認します。Backend API は Hibernate の統計を有効にしており（hibernate.generate_statistics: true）、トランザクションが終わるたびに Session Metrics をログに出します。Prometheus のスクレイプ（15 秒ごと）も SQL 1 本のセッションを大量に書くため、最後の 1 行ではなく直近 30 セッションの最大値 を取ります。

grep '"logger_name":"org.hibernate.engine.internal.StatisticalLoggingSessionEventListener"' backend-api/logs/backend-api.log \
  | tail -30 | jq -r '.message' | grep -oE 'executing [0-9]+ JDBC statements' | sort -k2 -n | tail -1
Get-Content backend-api/logs/backend-api.log |
  Where-Object { $_ -match 'StatisticalLoggingSessionEventListener' } |
  Select-Object -Last 30 | ConvertFrom-Json |
  ForEach-Object { $_.message -split "`n" } |
  Where-Object { $_ -match 'executing (\d+) JDBC statements' } |
  Sort-Object { [int]([regex]::Match($_, 'executing (\d+) JDBC').Groups[1].Value) } |
  Select-Object -Last 1

注意

ローカルの Docker では DB がすぐ隣にいるため、202 本でも SQL の合計実行時間は数十 ms（講師環境での実測で 24〜37 ms）で、レスポンスタイムだけを見ていると気づきません。本番のようにアプリと DB がネットワーク越しにある環境では、この本数がそのまま遅延になります。だから 本数で測ります。
