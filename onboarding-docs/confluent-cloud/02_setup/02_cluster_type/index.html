2. 初期設定

クラスタータイプを選択する

5種類の Kafka クラスタータイプの特徴と、選択時に押さえておくべき制約を説明します。
最終更新: 2026/8/12

IBM Confluent Cloud には5種類の Kafka クラスタータイプがあります。タイプの変更は原則としてできないため、この選択は初期設定の中で最も重要な判断のひとつです。

Step 1: タイプの特徴を比較する

タイプ用途容量単位
Basic検証、初期開発、小規模用途eCKU（エラスティック）
Standardパブリックネットワークを使う本番ワークロードeCKU
Enterpriseプライベートネットワークが必要な本番ワークロードeCKU
Freight高スループットかつレイテンシー要件が緩いコスト最適化ワークロードeCKU
Dedicated高トラフィックまたは専有容量・手動スケーリングが必要なミッションクリティカル用途CKU（専有）

Basic / Standard / Enterprise / Freight は負荷に応じて自動的に伸縮します（エラスティック）。使用量が最小値を下回る場合は課金されません。Dedicated は CKU 単位で容量を確保し、Single-Zone は最小 1 CKU、Multi-Zone は最小 2 CKU です。

作成画面では5種類のタイプが横並びで表示され、Standard に「Recommended」ラベルが付きます。各タイプの時間単価もこの画面で確認できます（単価はリージョンにより異なります）。また、画面下部で Uptime SLA を 99.9%（開発・ステージング向け）と 99.99%（本番向け）から選択でき、99.99% を選択すると最小 eCKU が 2 に設定されます。右側のコストパネルには、想定される月額の目安と、未使用時には eCKU がゼロまでスケールして課金されない旨が表示されます。

Step 2: 制約を確認する

【重要】タイプの変更は Basic から Standard へのアップグレードのみです

Basic から Standard へのアップグレード以外のタイプ変更はサポートされていません。 Standard から Basic へのダウングレードもできません。タイプを変更したい場合は、新しいクラスターを作成してデータを移行する必要があります。

そのほかの主な制約は次のとおりです。

項目内容
ブローカー設定の変更Dedicated のみ可能です。他のタイプは Topic レベルの設定で対応します
RBACBasic は Kafka クラスター内リソースの RBAC に対応していません
パーティション上限Enterprise は 96,000（うち compacted は 32,000 まで）。eCKU あたりの compacted 上限は 1,000 で、これを超えると総パーティション数が範囲内でも追加の eCKU が必要になります
課金Dedicated の拡張・縮小時は、容量変更の翌時間から新しい CKU 数で課金されます

【参考】そのほか作成画面で確認できること

  • Enterprise は AWS / Microsoft Azure / Google Cloud の3クラウドで選択でき、選択したクラウドに応じてプライベートネットワーク方式（PrivateLink / Private Link / Private Service Connect）が Summary に表示されます。
  • Advanced settings に削除保護（Enable deletion protection）のトグルがあり、有効にすると誤操作によるクラスター削除を防げます。削除は復元できないため、本番クラスターでは有効化を推奨します。

Step 3: スケーリング特性を確認する

Enterprise クラスター

Enterprise は主要クラウドで最大 32 eCKU まで自動的にスケールし、合計 7.5 GB/s を超えるスループットに対応します。

ただしスケールの速度には段階があります。10 eCKU までは数秒で拡張しますが、それを超える範囲はオンデマンドモデルとなり、1 eCKU あたり最大20分かかる場合があります。急激なトラフィック増加が見込まれるワークロードでは、事前に Confluent の担当チームへご相談ください。

Freight クラスター

Freight はコスト最適化を目的としたタイプで、次の制約があります。

  • 提供クラウドは AWS のみで、リージョンも一部に限られます（実機確認では Azure / Google Cloud は選択できず、東京・大阪リージョンも選択肢にありません。2026年8月時点）。未提供のリージョンはリクエストが可能です
  • クライアント側の最適化が必須です
  • スケールは10分あたり 4 eCKU（ingress 240 MBps / egress 720 MBps 相当）程度が目安です

【重要】Freight はトランザクションに対応していないため、Freight クラスターへの書き込みでは Exactly-Once Semantics（EOS）を利用できません。 Apache Flink から Freight の Topic に書き込むジョブは、障害シナリオによっては重複レコードを生成する可能性があります。なお、Freight からの読み取りはこの影響を受けません。

【参考】キューイング用途を想定する場合

Queues for Kafka（メッセージキュー相当の機能）は Enterprise および Dedicated クラスターで利用可能です。Standard クラスターへの対応は 2026年下半期の予定とされています。キューイング用途を前提とする場合は、クラスタータイプの選定に影響します。詳細は キューイング用途で利用する をご確認ください。
