監視とクォータを管理する

メトリクスの取得、コンシューマーラグの監視、サービスクォータの確認方法を説明します。
最終更新: 2026/8/12

Step 1: 監視の手段を選択する

手段概要
Metrics APIクラスターおよび Topic 単位のメトリクスを取得します。/export エンドポイントの遅延は約3分です
コンシューマーラグの監視Confluent Cloud Console から確認します
サードパーティ連携Datadog、New Relic などの監視ツールへの連携、およびログのエクスポートに対応しています
Dedicated クラスターの監視性能と拡張の管理、プリンシパル単位の利用量トラッキングが可能です

クラスター単位の日常的な監視は、クラスターの Monitor タブが起点になります。Throughput（Production / Consumption）、eCKU Usage、Cluster Demand（接続数）、Connection Behavior、パーティション構成などをウィジェットで確認できます。eCKU Usage は実際の消費量を示すため、コストのガードレールを設定する で説明した最大 eCKU の設定値を検討する際の実測データとしても利用できます。

参考：Log and Monitor（英語）

Step 2: サービスクォータを確認する

IBM Confluent Cloud には、リソースごとにサービスクォータが定義されています。現在値は次の方法で確認できます。

  • Confluent Cloud Console
  • Confluent CLI
  • Service Quotas API

クォータの上限に近づいた場合の通知設定については、コストのガードレールを設定する をご確認ください。

【参考】Kafka Streams アプリケーションの監視

Streams Rebalance Protocol（KIP-1071）を利用すると、リバランスの所要時間が短縮されるとともに、ブローカー側のメトリクスによってリバランスの性能とグループの健全性を Confluent Cloud Console および Metrics API から確認できます。

利用には Kafka Streams クライアント 4.2 以降と、アプリケーション側での group.protocol の設定が必要です。対応するクラスタータイプは Dedicated および Enterprise です。

Step 3: リリース情報を追跡する

IBM Confluent Cloud は SaaS のため、機能の追加・変更が随時反映されます。リリースノートは継続的に更新されており、四半期ごとにローンチ情報がまとめられています。

運用中の環境に影響する変更を把握するため、定期的にご確認ください。
