既存の Kafka から移行する

KCP（Kafka Copy Paste）を使った移行の流れと、Cluster Linking の前提条件を説明します。
最終更新: 2026/8/12

Step 1: 移行手段を選択する

既存の Kafka 環境から IBM Confluent Cloud へ移行する主な手段は次のとおりです。

手段概要
KCP（Kafka Copy Paste）ホスト型 Kafka からの移行を自動化する無償のオープンソース CLI ツールです
Cluster Linkingクラスター間でデータをミラーリングします
ReplicatorKafka のデータをコピーします

Step 2: KCP で移行を進める

KCP は移行作業を次の4段階で自動化します。

段階内容
1. 調査と計画既存の Kafka 環境をスキャンし、クラスター構成の検出と実使用量に基づくコスト把握を行います。Confluent の TCO 計算機への入力値を生成します
2. インフラ構築同等の Confluent Cloud クラスター、ネットワーク、移行用インフラを構築する Terraform スクリプトを、事前入力済みの状態で生成します
3. データ移行セキュアな外部 Cluster Linking によるレプリケーションを自動化します。ACL、コネクター、Schema Registry のデータも変換して移行します
4. クライアント移行Confluent Cloud Gateway（クラウドネイティブな Kafka プロキシ）を用いたクライアントの切り替えが予定されています

コスト見積もりを依頼する

Confluent Cloud の Migration hub（https://confluent.cloud/migration-hub）に、KCP が生成した kcp-state.json をアップロードすると、現状に基づく詳細なコスト見積もりを Confluent の担当者に依頼できます。

Migration hub の画面では、既存の Kafka / Confluent Platform クラスターから Topic をミラーリングして実データで性能・互換性を評価するためのクラスターリンク作成、ステップバイステップの移行ガイドのダウンロード、および見積もり依頼（Get a quote）の導線が提供されています。

参考：KCP（Kafka Copy Paste）（英語）

Step 3: Cluster Linking の前提条件を確認する

【重要】リンクの宛先にできるクラスタータイプは限られます

クラスターリンクは宛先（destination）クラスター側で作成・管理する必要があり、宛先にできるのは Dedicated または Enterprise クラスターのみです。

そのほかの制約は次のとおりです。

  • Basic / Standard クラスターは「宛先起動型リンク」のソースにはなれますが、「ソース起動型リンク」のソースにはなれません
  • Freight クラスターは、AWS のプライベートネットワーク構成でのみ、リンクのソースまたは宛先として利用できます

移行の計画を立てる前に、この制約が要件と整合するかをご確認ください。

参考：Cluster Linking on Confluent Cloud（英語）

【参考】ハイブリッド構成での運用

オンプレミスの Confluent Platform とクラウドを併用する場合は、次の機能が利用できます。

  • Cluster Linking による Bridge-to-Cloud 構成：オンプレミスとクラウドの間でデータを連携します
  • Unified Stream Manager（USM）：Confluent Platform のリソースを Confluent Cloud から一元的に監視・管理します
